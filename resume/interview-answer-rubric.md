# 高级后端面试命题与评分规范

## 1. 适用范围与目标

本规范适用于每日 LawStation 项目题与 Go/后端通用题的命题、追问、评分和答案分析。目标是检验高级工程师所需的分析能力：能否识别约束，讲清机制和因果关系，做出有依据的取舍，识别失败边界，并给出验证与演进方案。

LawStation 是练手项目。项目方向题以 RAG、AI Agent 的常见面试知识（概念、原理、机制和常见取舍）为主，只用 LawStation 的法律问答场景作少量例子。无需深入项目模块设计、完整链路或生产化改造，也不考查对项目数字或代码细节的记忆。

每次命题和评分前都应完整读取本规范。题型结构是回答提示和评分依据，而不是要求候选人机械套模板。

## 2. 总体原则

1. **先判断题型，再选择最小充分结构。** 简单问题用简洁答案即可；复杂问题才要求完整展开。
2. **一道题聚焦一个主要能力点。** 最多包含两个紧密相关的子问题，其余深度通过回答后的追问展开。
3. **高级水平看推理质量，不看术语数量。** 重点评价约束、因果、权衡、边界、验证和演进。
4. **只按题目实际要求评分。** 未被询问的维度不扣分；回答简短但准确、完整，同样可以获得高分。
5. **允许多种合理方案。** 只要假设明确、逻辑自洽、风险可控，就不能仅因与参考答案不同而扣分。
6. **区分当前实现与生产方案。** 能说明练手项目的合理简化、适用边界和生产化路径，是加深答案的重要方式。
7. **不把表达长度当成技术深度。** 重复题意、堆砌名词和无关扩展不加分。

## 3. 题型与最小充分回答结构

以下结构中的项目并非每题都必须出现。命题时先标记主类型，再明确本题的“必答点”和“高级加分点”。

### 3.1 简单概念题

适用于定义、作用、区别中的单一知识点。

建议结构：

1. 用一句话给出准确结论或定义。
2. 补充 2—3 个决定性特征。
3. 仅在有助于消除歧义时，给一个边界或短例子。

参考回答时长：30—60 秒。不要为了显得完整而强行加入架构、监控或演进方案。

### 3.2 原理与机制题

适用于“为什么有效”“内部如何运转”“如何保证某种性质”。

建议结构：

1. 要解决的问题或目标。
2. 核心流程与关键参与者。
3. 关键不变量、因果关系或成立条件。
4. 失败边界及其工程影响。

参考回答时长：1—3 分钟。

### 3.3 对比与选型题

适用于技术方案比较、组件选择和架构决策。

建议结构：

1. 明确业务场景、约束和优先级。
2. 沿与场景相关的维度比较候选方案。
3. 给出选择及理由。
4. 说明代价、不适用条件和切换信号。

参考回答时长：2—4 分钟。没有约束的“谁更好”通常不是有效结论。

### 3.4 故障排查与性能分析题

适用于线上故障、性能退化、稳定性和数据异常。

建议结构：

1. 界定现象、影响范围和时间线。
2. 按概率与影响对假设排序。
3. 说明用哪些证据逐层缩小范围。
4. 给出止损措施与根因修复。
5. 说明如何验证恢复并预防复发。

参考回答时长：3—5 分钟。不能只罗列可能原因，也不能在证据不足时直接下结论。

### 3.5 系统设计题

适用于新系统、重要子系统或较完整的架构改造。

建议结构：

1. 澄清功能需求、规模假设、关键 SLO 和约束。
2. 给出高层架构、数据流和核心数据模型。
3. 解释关键机制与接口边界。
4. 处理一致性、可靠性、故障恢复和幂等。
5. 按题目重点讨论容量、性能、可观测性与安全。
6. 总结主要取舍、瓶颈和分阶段演进路径。

参考回答时长：5—10 分钟。无需平均展开所有维度，应把时间留给本题的核心矛盾。

### 3.6 项目与工程实践题

适用于项目介绍、技术决策、个人贡献和工程复盘。

建议结构：

1. 交代背景、目标和约束。
2. 说明个人职责与决策范围。
3. 解释核心决策、候选方案和取舍。
4. 描述落地过程、主要风险与验证方法。
5. 说明结果、局限、反思和下一步演进。

参考回答时长：3—6 分钟。结果可以是定性验证、实验观察或工程收益，不要求背诵具体数字。

### 3.7 实验与评测题

适用于 RAG、Agent、模型能力、检索质量和架构改造的效果验证。

建议结构：

1. 明确待验证的假设和成功条件。
2. 说明数据集、基线、对照变量和实验流程。
3. 说明指标如何计算、各自代表什么，以及为什么适合该目标。
4. 分析结果、失败样本、偏差来源和有效性威胁。
5. 说明评测结果如何支持上线、回滚或继续迭代的决策。

参考回答时长：3—5 分钟。重点是评测设计与指标含义，不要求记忆项目中的准确率、样本量、阈值或其他实验数字。

### 3.8 混合题

复杂题可能同时涉及多个类型。评分前必须确定一个主类型，只引入解题所必需的次类型结构，不能把所有结构叠加成固定模板。

## 4. 每日命题标准

每天共 5 题：

- 项目方向 2 题：通常为 1 题 RAG、1 题 AI Agent 常见面试知识；以通用原理为主体，轻度结合 LawStation。
- Go/后端 3 题：覆盖基础原理与工程应用，跨天轮换 Go、数据库、缓存、网络、消息队列、系统设计和故障排查等主题，不把原来 5 题压缩捆绑成 3 道大题。

继续按照高级工程师水平评分，但优先选择概念、原理和范围明确的场景题。减少题量和项目细节，不以增加单题复杂度补偿。每题最多两个紧密相关的小问题，追问也应克制。

### 4.1 项目题边界

项目题应优先询问：

- RAG 的基本流程、分块、Embedding、稀疏与稠密检索、混合检索、重排序等常见原理；
- AI Agent 与固定工作流的区别、工具调用、ReAct、规划、记忆和上下文等常见概念；
- 一个通用机制的作用、成立条件和主要取舍；
- 常见评测指标怎样计算、代表什么，以及基本局限。

每题只从上述范围中选择一个主要知识点。项目关联最多用一个简短场景或举例要求，不应依赖项目知识才能作答。默认不要求设计 LawStation 的具体模块、审查回路、故障状态机或完整生产化方案；用户主动要求深入时，再围绕当前题展开。

项目题不应询问或要求记忆：

- 具体准确率、召回率、样本数量、延迟或吞吐数字；
- 具体模型版本、参数、阈值和配置常量；
- 文件名、函数名、代码行或局部实现细节；
- 只有阅读当前代码才能知道、且不具可迁移价值的事实。

例如：“向量检索与关键词检索各有什么优缺点？法律问答中为什么可能结合两者？”或“Function Calling 与 Agent 有什么区别？”评测题可问“Recall@K 如何计算、说明什么？”，不要求提交项目完整评测设计或背诵具体实验数字。

### 4.2 命题前检查清单

每道题展示前都必须通过以下检查：

- 不依赖背诵项目数字、配置或代码细节；
- 项目方向题以 RAG / AI Agent 通用知识为主，项目仅作轻量例子，未暗中变成项目详细设计题；
- 只有一个清晰的主要能力点，最多两个紧密相关的子问题；
- 能在该题型的参考时长内给出完整回答；
- 考查的是可迁移知识、方法或决策能力；
- 允许存在多种有条件的合理答案；
- 不包含未经说明的隐藏前提；
- 已为本题写明主类型、必答点和高级加分点；
- 与近期题目不重复，或具有明确的新角度；
- 更深的旁支可以留到回答后的追问中。

任一项不满足时，应先改写题目再展示。

### 4.3 小红书面经来源

优先参考小红书平台上 AI Agent / RAG 应用开发岗位的面经，不局限于“小红书公司”的岗位。来源索引见同目录 interview-sources.md，生成新题组前读取并优先复用已核验考点，必要时再搜索补充。

- 通过可访问的笔记原文或图片核实考点，记录标题、作者、链接、页面显示日期和实际阅读范围。只读了图片首页时，不声称读完整篇。
- 标注为“作者自述面经考点改编”，不把经历真实性、企业归属或所谓高频当成已独立验证的事实。平台 AI 总结、搜索摘要、转载和营销题库不能冒充原帖。
- 提取通用知识点后按本规范改写，保留来源链接；避免整篇搬运，不照抄帖子答案。技术参考答案和评分依据应通过官方文档、原始论文等一手技术资料核验。
- 每天仍是 2 道 RAG / Agent 题与 3 道 Go / 后端题；过滤项目深挖、具体数字和手写代码要求。Java 等语言特有题不直接用于 Go 定位。
- 登录失效或页面不可访问时，说明限制，使用已保存的已核验考点，不声称完成了新的小红书检索。

## 5. 十分制评分标准

### 5.1 通用分档

- **0—3 分：** 核心概念错误、答非所问，或方案在基本条件下不可行。
- **4—5 分：** 知道相关概念，但缺少关键机制、因果链或场景判断。
- **6—7 分：** 主体正确，覆盖主要必答点，能够解决常规问题，但边界、验证或取舍仍不充分。
- **8 分：** 回答完整且有条理，能结合约束说明机制、取舍和主要风险，达到高级工程师的合格表现。
- **9 分：** 在 8 分基础上，主动识别关键边界、失败模式和验证方法，判断具有较强工程可信度。
- **10 分：** 准确、凝练且深入；能抓住核心矛盾，比较替代方案，并给出可落地的决策和演进路径。10 分不要求答案很长。

评分是整体判断。单个措辞或遗漏不自动触发机械封顶，应根据其是否破坏答案的核心正确性决定影响。

### 5.2 分题型权重

| 主类型 | 评分维度与权重 |
| --- | --- |
| 简单概念 | 核心正确性 6；决定性特征 2；边界或例子 1；表达 1 |
| 原理机制 | 核心正确性 3；流程与因果 3；不变量或边界 2；工程影响 1；表达 1 |
| 对比选型 | 场景约束 2；比较准确性 2；选择与取舍 4；风险或切换条件 1；表达 1 |
| 故障排查 | 问题界定 1；假设与证据 3；定位路径 2；止损与修复 2；验证与预防 1；表达 1 |
| 系统设计 | 需求与假设 1；架构与数据流 2；一致性与可靠性 2；容量与性能 1；取舍与演进 2；可观测性或安全 1；表达 1 |
| 项目实践 | 背景与职责 1；决策与技术推理 3；落地与风险 2；验证与结果 1；局限与演进 2；表达 1 |
| 实验评测 | 假设与实验设计 2；数据、基线与对照 2；指标计算与含义 2；失败分析与局限 2；决策应用 1；表达 1 |

如果题目明确缩小了范围，应按比例重新分配无关维度的权重，不能因候选人未回答题目之外的内容而扣分。

### 5.3 必答点与高级加分点

命题时内部记录两层标准：

- **必答点：** 直接回答问题所需的核心结论、机制和必要边界，决定答案能否达到 6—8 分。
- **高级加分点：** 重要的取舍、失败模式、验证方法、演进策略或反直觉洞察，用于区分 8—10 分。

高级加分点不能成为未提前限定场景的隐藏必答项。候选人给出不同但成立的高级洞察时，应等价计分。

### 5.4 评分公平性

- 先按回答内容复述候选人的主张，再判断缺口，避免用参考答案替换候选人的语义。
- 问题存在歧义时，接受合理解释；必要时先追问，不能按未说明的前提扣分。
- 对不确定性作出准确限定，比无依据地给出确定结论更好。
- 实验指标的具体历史数值不是评分项；方法、计算、含义、局限和决策用途才是评分项。
- 不设置针对练手项目陈述的特殊分数上限，按本题实际能力点统一评分。
- 合成数据、工程样例和 LLM Judge 可以作为评测工具；相关题目应考查它们能证明什么、不能证明什么，而不是把某类工具本身视为扣分项。

## 6. 回答后的反馈结构

### 6.1 简单题

按以下顺序简洁反馈：

1. 题型与得分。
2. 回答正确的部分。
3. 一个最关键的缺口或修正。
4. 一版精炼参考答案。

### 6.2 复杂题

按以下顺序反馈：

1. 题型、得分和一句话结论。
2. 回答正确且有价值的部分。
3. 未覆盖或不准确的必答点。
4. 可以提升到高级水平的加分点。
5. 最值得继续讨论的风险或追问。
6. 与题型相匹配的结构化参考答案。

反馈篇幅应与题目复杂度和答案缺口成比例。不要为了完整而逐项重复候选人已经说清楚的内容。

首次得分以首次完整回答为准。讨论中候选人补充或修订答案后，只有在其要求重新评分时，才另行给出“修订后得分”，并保留两次得分的区别。

## 7. 单题讨论流程

1. 新题组先列出当天 5 道题的标题，只完整展示第 1 题。
2. 候选人回答后，按本规范评分、给出答案分析，并围绕当前题继续讨论。
3. 追问应针对当前答案中最有价值的一个缺口，不应突然扩展成新的综合题。
4. 只有候选人明确说“下一题”或“跳过”时，才展示下一题。
5. 当天题组未完成时，下一次提醒继续当前进度，不另起一套重复题。
6. 用户说“今天先到这里”时停止出题和追问，保留进度，不补发题目。每日提醒仍按原时间执行，除非用户明确要求暂停提醒。

## 8. 评分前最终自检

评分者在输出反馈前确认：

- 已识别主题型，并采用对应的最小充分结构；
- 只评价题目实际询问的内容；
- 正确区分必答点与高级加分点；
- 没有把答案长度、术语数量或具体数字当作高级水平；
- 已接受假设清晰、逻辑自洽的替代方案；
- 参考答案展示的是一种高质量思路，而不是唯一标准答案；
- 反馈复杂度与题目复杂度相称；
- 没有在候选人明确提出前推进到下一题。
