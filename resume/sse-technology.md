# Server-Sent Events（SSE）技术原理

> 本文先脱离 LawStation 讲清 SSE 本身：协议格式、浏览器消费、断线恢复、心跳、顺序语义、代理配置、安全边界，以及它与 WebSocket、轮询和普通流式 HTTP 的区别。项目代码实现见 [LawStation SSE 代码导读](sse-code-guide.md)。

## 1. SSE 解决什么问题

SSE（Server-Sent Events）是一种基于 HTTP 的服务端单向推送机制。客户端先建立一个持续存在的 HTTP 请求，服务端保持响应不结束，并不断向响应体追加事件。

典型使用场景包括：

- AI 回答进度与文本分片；
- 后台任务状态；
- 构建进度；
- 日志、通知和监控指标；
- 只需要“服务器推送给浏览器”，不需要同一连接双向通信的业务。

SSE 的逻辑方向是：

```text
客户端通过普通 HTTP 请求发送命令
→ 服务端通过 SSE 长连接持续返回事件
```

它不是新的传输层协议，而是约定使用：

```http
Content-Type: text/event-stream
```

的流式 HTTP 响应。

## 2. SSE 的报文格式

一个 SSE 事件由若干文本字段组成，以空行结束：

```text
id: 17
event: agent_status
data: {"agent":"legal_researcher","status":"researching"}

```

常见字段：

| 字段 | 作用 |
|---|---|
| `event` | 事件类型；客户端可据此分发处理 |
| `data` | 事件载荷；协议本身只认文本，JSON 是应用层约定 |
| `id` | 事件游标；可用于断线续传 |
| `retry` | 建议原生 EventSource 的重连等待时间 |
| `:` 开头 | Comment；客户端不当作业务事件，可用作心跳 |

多行 `data` 会以换行拼接：

```text
event: message
data: 第一行
data: 第二行

```

客户端得到的数据是：

```text
第一行\n第二行
```

需要注意：TCP/HTTP 数据块边界不等于 SSE 事件边界。一次 `read()` 可能只读到半个事件，也可能同时读到多个事件。因此客户端必须维护缓冲区，并以空行切分完整事件。

## 3. 建立连接的两种客户端方式

### 3.1 原生 EventSource

浏览器提供 `EventSource`，适合标准 GET SSE：

```javascript
const source = new EventSource('/api/events');
source.addEventListener('token', (event) => {
  console.log(event.data);
});
```

优点：

- 浏览器自动重连；
- 自动维护 `Last-Event-ID`；
- API 简单。

限制：

- 只适合 GET；
- 不能自由设置任意请求头；
- 对自定义错误处理、AbortController 和复杂身份头控制不够灵活。

### 3.2 fetch + ReadableStream

需要自定义 Header、POST Body、显式取消或自行控制重连时，可以使用：

```javascript
const response = await fetch('/api/events', {
  headers: { Authorization: 'Bearer ...' },
  signal: controller.signal,
});

const reader = response.body.getReader();
```

此时浏览器不会自动提供完整 SSE 语义，应用需要自己实现：

- 字节流解码；
- 跨 chunk 缓冲；
- `event/data/id` 解析；
- 断线重连；
- 游标保存与重复事件过滤；
- HTTP 非 2xx 错误处理。

## 4. 服务端实现要点

服务端应返回持续生成内容的异步迭代器，并至少设置：

```http
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

其中：

- `no-cache` 避免中间层缓存旧事件；
- `keep-alive` 表明希望保持连接；
- `X-Accel-Buffering: no` 用于提示 Nginx 不要等缓冲区积满后再统一发送。

服务端每次输出的事件必须完整结束于两个换行：

```python
yield f"event: token\ndata: {json_payload}\n\n"
```

如果反向代理仍启用了响应缓冲，服务端虽然持续 `yield`，浏览器也可能很久才看到数据。因此验证 SSE 时不能只看应用代码，还应检查代理超时、缓冲和网关空闲连接设置。

## 5. 心跳为什么必要

模型调用或后台任务可能几十秒没有新业务事件。代理、负载均衡器或浏览器网络层可能把这种空闲连接视为失效。

常见保活方式是定期发送 Comment：

```text
: heartbeat

```

Comment 的特点：

- 会产生网络字节，刷新中间层空闲计时；
- 不属于业务事件；
- 不应占用事件序号；
- 不应写入任务事件数据库；
- 客户端 parser 应忽略。

SSE 心跳只表示“HTTP 连接仍可用”，不能证明后台任务仍正常运行。任务存活应由任务状态、租约或独立健康机制判断。

## 6. 断线恢复与事件重放

SSE 连接可能因刷新、Wi-Fi 切换、代理超时或移动网络变化而中断。可靠恢复通常需要三个组件：

```text
服务端为事件分配递增 id
客户端保存最后成功消费的 id
重连时携带 Last-Event-ID 或查询游标
```

例如客户端已经处理到 `id=17`：

```http
GET /api/events?after_sequence=17
Last-Event-ID: 17
```

服务端查询：

```sql
WHERE sequence > 17
ORDER BY sequence
```

然后先重放缺失历史，再继续等待实时事件。

### 6.1 交付语义

网络系统很难仅靠 SSE 保证严格 exactly-once。常见实现是：

- 服务端提供按 ID 的可重放事件；
- 客户端按 ID 去重；
- 业务结果本身使用幂等写入。

这样形成接近“至少一次传输 + 客户端幂等消费”的语义。若连接在客户端处理事件后、保存游标前断开，该事件可能再次到达；所以事件处理不能只依赖“服务器肯定只发一次”。

### 6.2 顺序边界

单条 SSE 连接内字节顺序由 HTTP/TCP 保证，但应用仍需明确：

- 顺序是全局的，还是仅在某个任务内递增；
- 多个 Worker 是否可能并发分配同一序号；
- 序号和事件写入是否在同一事务内完成；
- 事件保留多久，过期后是否还能恢复。

对长任务而言，“每个任务独立 sequence”通常比全局序号更容易隔离和查询。

## 7. SSE 与后台任务必须解耦

一个常见反模式是：

```text
SSE 请求协程本身执行耗时任务
→ 浏览器断线
→ 请求协程被取消
→ 后台任务也被取消
```

如果产品要求刷新、切换页面或暂时断网后任务仍继续，应拆成：

```text
创建持久任务
→ 独立 Worker 执行
→ 事件写入持久日志
→ SSE 只是订阅任务事件
```

此时：

- 断开 SSE 只停止观察；
- 明确的 Cancel API 才取消任务；
- 重新订阅可从事件游标恢复；
- 服务重启后可结合任务表和执行 Checkpoint 续跑。

SSE 本身不提供任务队列、持久化、幂等或故障恢复，这些都属于应用层设计。

## 8. 错误与终态设计

SSE 已经返回 HTTP 200 后，后续业务异常不能再修改 HTTP 状态码。因此通常定义应用事件：

```text
event: error
data: {"message":"回答生成失败"}

event: message_end
data: {"status":"failed"}
```

建议区分：

- 建连前错误：使用 400/401/404/409/500；
- 建连后错误：使用安全的 `error` 事件；
- 终态：使用统一结束事件和服务端任务状态；
- 网络中断：不是业务失败，应尝试带游标重连。

客户端不能把“ReadableStream 正常结束”直接等同于“业务成功”，还应查询或读取明确终态。

## 9. 安全与隐私

SSE 与普通 HTTP API 一样需要所有权校验。尤其是可重放事件接口，不能只凭公开的任务 ID 返回历史事件。

建议：

- 在开始流式响应前完成身份和资源所有权校验；
- 查询事件时同时限定租户、用户和任务；
- 不把模型内部推理、工具密钥、数据库连接串写入事件；
- 错误事件只返回安全摘要，不返回内部堆栈；
- 限制单用户连接数，避免长连接耗尽资源；
- 对跨域请求正确配置 CORS 和凭证策略；
- 对事件正文做与普通 API 相同的数据分级和脱敏。

## 10. SSE 与其他方案比较

| 方案 | 通信方向 | 复杂度 | 自动重连 | 适合场景 |
|---|---|---:|---|---|
| 短轮询 | 客户端周期请求 | 低 | 应用实现 | 低频状态、兼容性优先 |
| 长轮询 | 服务端延迟响应 | 中 | 应用实现 | 事件较少、无法使用流式响应 |
| SSE | 服务端单向推送 | 中 | EventSource 原生支持 | AI 进度、通知、任务事件 |
| WebSocket | 全双工 | 高 | 应用实现 | 高频双向协作、实时控制 |
| Webhook | 服务端到服务端 | 中 | 依赖重试策略 | 异步系统集成，不面向浏览器长连接 |

对于“用户通过 REST 发起 Agent 任务，服务器持续推送状态与结果”的场景，SSE 通常比 WebSocket 更简单：命令仍由普通 API 完成，推送链路保持单向。

## 11. 可观测性指标

生产环境应至少记录：

- 建连成功率；
- 活跃 SSE 连接数；
- 连接持续时间；
- 首事件、首正文和总完成延迟；
- 重连次数；
- 重放事件数；
- 重复事件丢弃数；
- 心跳发送数；
- 客户端主动取消与意外断线数量；
- 每个任务的最后事件序号与终态。

这些指标分别回答“连接是否稳定”“任务是否在运行”“用户何时看到内容”“恢复机制是否有效”，不能只用一个总耗时替代。

## 12. 常见误区

1. **把 HTTP chunk 当成完整 SSE 事件**：事件可能跨多个 chunk，必须缓冲解析。
2. **把心跳当作任务健康**：心跳只保持连接，任务可能已经卡死。
3. **断线即取消任务**：只有在产品明确采用连接绑定语义时才合理。
4. **没有事件 ID 却声称支持恢复**：重新连接不等于重放缺失事件。
5. **只依赖服务端不重复发送**：客户端仍应按事件 ID 幂等处理。
6. **在流开始后抛 HTTP 错误**：此时只能发送应用层错误事件。
7. **忽略代理缓冲**：应用端持续 yield 不代表浏览器实时收到。
8. **把分片输出等同于模型实时 token**：服务可以在完整结果审核后再人为分片。

## 13. 一句话理解

> SSE 是建立在 HTTP 上的服务端单向事件流；它负责传输，不负责后台任务可靠性。真正可恢复的 Agent 流需要额外组合持久任务、事件序号、历史重放、幂等消费和明确取消语义。
