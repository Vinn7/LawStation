# Agent / RAG 评测方法论

> 面向：知道"要给 AI 系统做评测"这个大方向，但没亲手设计过消融实验、没被 LLM-as-Judge 的偏差坑过的后端工程师。
> 目标：搞清楚"这个功能有没有用"这句话背后需要多严谨的实验设计才能回答；§4 附一份能直接拿去回答"你的项目是怎么评测的"这个面试问题的速答表。

## 0. 前置知识

建议在读完 [06-rag-hybrid-retrieval.md](06-rag-hybrid-retrieval.md) 和 [04-langgraph-stategraph.md](04-langgraph-stategraph.md) 之后再看本篇——本篇讲的是"怎么证明前面两篇讲的检索优化和 Agent 编排真的有效"，需要先知道被评测的对象是什么。本篇是整个系列的收尾：前面几篇讲"怎么做"，这篇讲"怎么知道做得好不好"。

## 1. 要解决的问题

一个多 Agent + RAG 系统改了一个组件（比如加了 Reranker、换了 Reviewer 策略），怎么知道这个改动是真的变好了，而不是"改完之后随手试了三个问题、看起来还行"？这里面藏着几个真实的坑：

- **只看几个成功案例**：挑出来展示的往往是效果最好的样本，天然带幸存者偏差。
- **换了一个组件，同时也换了别的东西**：如果对比实验里数据集、随机种子、模型版本没有全部固定，看到的差异可能来自无关变量，不是被测试的那个改动。
- **拿小样本结果说大话**：3 条样本测出来"调用率下降了 66%"，这句话本身没错，但脱离样本量语境说出来，很容易被理解成生产环境的稳定收益。
- **只测最终答案，看不出问题出在哪一环**：一个多阶段系统（检索 → 编排 → 生成 → 复核）出问题，如果只测端到端结果，很难定位是哪一层的锅。

## 2. 核心机制原理

### 2.1 分层测试：把系统拆成独立可测的层

行业里对多组件系统的通用做法是分层隔离测试，而不是每次都测整条链路：

- 只测最底层的组件本身（这里是检索器），排除上层逻辑的干扰；
- 用固定/模拟的下游输入测中间层（这里是三 Agent 编排），排除底层组件的波动；
- 最后再测完整链路做最终确认，成本最高、频率最低。

这和普通软件工程里"单元测试 / 集成测试 / 端到端测试"金字塔是同一个思路在 AI 系统评测上的映射，只是每一层测的不是"函数返回值对不对"，而是"检索到的候选对不对""生成的回答符合安全规则吗"。

### 2.2 两类评测方法：确定性规则 vs LLM-as-Judge

AI 系统的输出往往没有唯一"标准答案"，但这不代表所有维度都只能靠模型打分：

- **确定性 Evaluator**：能用代码逻辑判断对错的维度（引用是否可追溯、是否越权访问了别人的数据、循环次数是否超限）应该用规则判断——结果可复现、可以无限扩展到大样本，没有模型本身的偏差。
- **LLM-as-Judge**：只有代码规则确实判断不了的语义维度（回答是否清晰、是否切题、语气是否得当）才交给另一个模型打分。行业里 RAGAS、DeepEval、TruLens、Langfuse 都是把这两类方法组合起来的评测框架。

举一个具体场景帮助建立直觉：评测"回答里引用的法条 chunk，是不是都来自这一轮真实检索到的证据包"——这句话读起来像是需要理解语义，但拆开看，它其实只是一次集合包含关系判断（`引用的 chunk ID 集合 ⊆ 证据包里的 chunk ID 集合`），一行代码就能给出确定性的对错，交给模型判断反而是多余的成本。但换一个场景——"这段回答有没有把用户案情里的争议点都讲清楚"——没有一条能写成代码的规则能覆盖"讲清楚"这个语义判断，只能交给语言模型去理解上下文再打分。判断标准是：**能不能把"对不对"表达成一个不依赖语言理解、任何人复算都会得到同一个结果的谓词**——能，就该用确定性规则；不能，才值得花钱调用 Judge。

一个常见的方法论错误是"什么都交给 LLM 打分"——不仅成本高，还引入了下面这条要专门讲的偏差问题。

### 2.3 RAG 评测的四个经典维度：RAGAS 框架

开源框架 RAGAS 把 RAG 质量拆成四个可以独立衡量的维度，是这个领域里被引用最多的分解方式：

- **Faithfulness（忠实度）**：回答里的每个论断能不能由检索到的上下文支撑，衡量"有没有编造"。
- **Answer Relevancy（回答相关性）**：回答是否切题，衡量"有没有答非所问"。
- **Context Precision（上下文精确率）**：检索到的上下文里有多少是真正有用的，排在前面的是否更相关。
- **Context Recall（上下文召回率）**：标准答案所需的信息是否都出现在检索结果里。

这四个维度的价值在于**把"回答好不好"这个笼统问题拆成了检索质量和生成质量两个独立的、可以分别优化的子问题**——如果 Context Recall 低，问题在检索环节；如果 Context Recall 高但 Faithfulness 低，问题在生成环节没有忠实使用检索到的证据。

### 2.4 LLM-as-Judge 的已知偏差

用一个模型评价另一个模型的输出，天然带偏差，行业里总结出几类最常见的：

| 偏差 | 表现 | 常见缓解 |
|---|---|---|
| 位置偏差（Position Bias） | 成对比较时，Judge 倾向偏爱排在前面（或后面）的候选 | 交换两个候选的顺序各跑一次，取一致的结果 |
| 冗长偏差（Verbosity Bias） | 更长的回答容易被打更高分，即使信息量没有增加 | 打分标准里明确惩罚无关展开，或做长度归一化 |
| 自我偏好偏差（Self-preference Bias） | Judge 模型倾向偏爱和自己风格/训练分布接近的回答 | Judge 与被测模型使用不同家族/厂商的模型 |

这些偏差不是"用了 LLM Judge 就一定会犯"，而是设计评测时必须主动防范的已知风险点。

### 2.5 消融实验（Ablation Study）的基本纪律

消融实验的核心是**单变量控制**：固定其余全部条件（数据集、随机种子、模型版本、其他配置），只切换被测试的那一个变量，对比前后差异。行业里做严谨消融还会额外做**盲选/预注册**——决定"哪些样本进入最终对比"的规则，不能读取被比较双方的实际表现，否则等于在挑对自己有利的数据，这也是学术界"p-hacking"问题的工程对应版本。

### 2.6 业界一套"完善"的评测体系通常长什么样

在看本项目具体做了什么之前，先建立一个参照系——一套成熟的生产级评测体系，通常同时具备下面这几块，缺一块就是一处明确的差距（§7 会逐条对照本项目现状）：

1. **数据层**：核心基准集由真人标注（法律、医疗这类专业领域尤其重要），配合标注者间一致性（inter-annotator agreement）校验标注质量本身够不够可信；合成/派生数据可以补充覆盖度，但不能替代黄金集。
2. **分层评测**：§2.1 讲的单元/集成/端到端金字塔，成本和真实度递增、执行频率递减。
3. **确定性规则 + LLM Judge 组合**：§2.2 讲的划分原则；Judge 本身还要做偏差校准（多 Judge 投票、Position Bias 交换验证、Judge 和被测模型不同厂商）。
4. **消融/AB 实验纪律**：§2.5 讲的单变量控制 + 盲选，成熟团队还会加一步——**统计显著性检验**（比如置信区间、假设检验），判断观察到的差异是不是噪声。
5. **CI/CD 集成**：代码或 Prompt 变更时自动触发回归评测，有回归就阻断合并，而不是依赖人记得手动跑。
6. **线上持续监控**：对生产流量做抽样异步评测，配合隐式反馈（点赞/点踩/复制/重新提问）持续监控质量有没有随时间漂移。
7. **人工审核回流闭环**：低分/负反馈样本进入人工审核队列，审核结论回流成新的标注数据，形成"评测发现问题 → 人工确认 → 回流训练/评测集 → 再评测"的闭环，而不是评测完就结束。
8. **成本治理**：评测/线上采样有真正的执行前预算拦截（超限就不让跑），不是只在跑完之后记一笔账。
9. **可复现性**：数据集哈希、模型版本、代码版本、随机种子全部随报告归档，任何一次结论都能追溯回具体的代码和数据快照。

## 3. 本项目具体实现

> 这一节只讲"做了什么设计决策、为什么这么设计"，不逐行对照代码——面试不会问评测代码具体怎么写，问的是你有没有意识到这些坑、怎么设计出对应的机制。

**三层检测对象，外加一个不那么直观的设计**：`retrieval`（只测检索器，不经过 Agent）→ `component`（用固定 Fixture 工具结果测 Agent 编排，屏蔽真实检索波动）→ `live`（真实链路，成本最高、频率最低），对应 §2.1 的分层金字塔。`component` 层内部还有一个变化维度：要单独测 Reviewer 这一个 Agent 时，不是把它 Mock 掉，而是把它的上游产物（案情分析、证据包、草稿）冻结成固定输入，只让 Reviewer 在**真实生产代码路径**上跑——这样测出来的检出率波动只反映 Reviewer 自己的能力，不会混进上游 Researcher 检索是否命中之类的噪声，同时又不是脱离生产逻辑的纯 Mock。

**确定性规则覆盖什么**：一组规则函数负责"能用代码判断对错"的维度，大致分四类——路由/Schema 是否合法、检索质量（Recall@5/MRR/Hit-Rate 这类排序指标）、引用安全（引用的证据是否都能在证据包里找到）、其他安全约束（工具有没有被越权调用、循环次数有没有超限、是否用了已被替换的旧事实、有没有跨租户泄漏）。这类规则要求接近 100% 通过，不接受"大概符合"。

**LLM Judge 怎么打分**：语义维度（争议点覆盖、证据一致性、事实忠实度、风险校准、清晰度、帮助程度等）交给一个独立、关闭 Thinking 的模型实例评分，**一次请求同时返回多个维度的分数**，而不是每个维度单独发起一次调用——省成本的同时，也降低"每次单独问都倾向给高分"这种打分漂移的空间。

**RAG 消融：盲选资格筛选**：对比 RRF 和 BGE 精排效果时，先按一条完全不依赖 BGE 表现的规则（候选是否进入未启用精排的 Hybrid Top12、且命中至少两个预先声明的干扰片段）筛出正式挑战集，筛选阶段全程关闭 BGE，冻结之后才第一次跑对比实验——这是 §2.5"预注册"原则的具体落地，目的是让"这条样本值不值得测"这个决定完全独立于"BGE 测出来好不好看"。

**Reviewer 消融：把审核环节当分类器评测**：构造一批已知包含错误的草稿（伪造引用、编造金额、无依据断言等）和一批正常草稿，衡量 Reviewer 能不能正确识别（检出率）、会不会错杀正常草稿（误拒率），用检出率/误拒率这套二分类语言评测，而不是笼统看一个"通过率"。

**一个诚实的半成品**：项目里还有一套多轮/并发/断线重连场景的生成管线——用固定代码写死的场景蓝图（比如"用户切换会话时原任务要在后台继续跑""SSE 断线重连事件不能重复"），只让模型填充具体话术、不生成测试逻辑本身。已经生成并通过校验的场景目前**还没有被接到一个真正驱动 Agent 运行的执行器上**——数据生成和冻结管线是完整的，评测闭环的最后一环还没接上，这是当前体系里最值得主动承认、而不是含糊带过的差距。

**分级执行**：评测按成本分四级（零成本只跑确定性规则 → 本地真实调用 → 小样本云端对比 → 重大变更后的扩大样本），默认只跑最便宜的一级。值得诚实说明的一点：后两级在代码层面并没有真正的差异化逻辑，区别更多是团队使用约定而不是代码强制的门禁——这类"看起来分级、实际执行时全靠人工守规矩"的情况，本身就是个值得在 §7 里展开的生产化差距。

## 4. 面试速答："你的项目是怎么评测的？"

**30 秒版本**：我们把评测拆成三层——单独测检索器、用固定 Fixture 屏蔽检索波动测 Agent 编排、最后测真实端到端链路；安全类硬规则（引用有没有越界、有没有编造法条）用确定性代码判断，语义类维度（回答讲没讲清楚、风险提示够不够）用另一个独立模型打分；对比检索算法改动时，用盲选筛选保证挑选测试样本的规则不知道新方案表现如何，避免挑对自己有利的数据；单独测审核 Agent 时把它当分类器评测，看检出率和误拒率；报告里数据集哈希、索引指纹、模型版本、Git Commit 全部留痕，保证结论可复现。

**每类评测对象的具体做法**：

| 评测对象 | 评测方法 | 评测指标及含义 | 评测结果 |
|---|---|---|---|
| 检索器（RAG 混合检索质量） | 固定数据集/索引指纹/随机种子的消融实验（BM25 vs Hybrid vs BGE 精排），Reranker 对比额外用盲选筛选构造挑战集 | **Recall@5**：期望的正确文档有多大比例出现在前 5 个结果里；**MRR**（平均倒数排名）：第一个命中结果排名倒数的均值，越接近 1 说明正确答案排得越靠前；**Hit@1/Hit@3**：前 k 个结果里命中的比例 | 口语化语义挑战集（n=300）：Recall@5 从 86.67% 提升到 96.33%，MRR 从 0.77 提升到 0.87；BGE 精排挑战集（n=200）：Hit@1 从 95% 提升到 97%，代价是平均检索耗时增加约 1.3 秒 |
| 三 Agent 编排（路由/结构/安全） | 固定 Fixture 工具结果隔离检索波动，批量跑确定性规则 | Schema 合法性、路由正确率、引用归属（citation grounding，引用的证据是否都在证据包里）、循环次数是否超限、有没有跨租户泄漏等 | 安全类规则要求接近 100% 通过，是硬门禁而不是参考指标 |
| Reviewer（审核 Agent 单独消融） | 构造已知包含错误的草稿 + 正常草稿混合集，冻结上游产物只跑 Reviewer 这一段，当分类器评测 | **检出率**（Recall）：真正有问题的草稿里，Reviewer 正确拦下的比例；**误拒率**（False Rejection Rate）：正常草稿被错误拦下的比例；**动作准确率**：给出的处理动作是否恰当 | 检出率 87.5%，低于内部 90% 的门禁目标——报告如实标注"未达标"，不换个说法回避 |
| 回答质量（语义维度） | LLM-as-Judge，独立、关闭 Thinking 的模型实例，一次请求同时打多个维度分 | 争议点覆盖、证据一致性、事实忠实度、风险校准、完整性、行动性、清晰度、帮助程度，1-5 分归一化 | 用于跟踪某次改动前后回答质量的相对变化，不作为独立发布门禁 |
| 多轮/并发/断线重连场景 | 代码写死场景蓝图，LLM 只填充话术，通过敏感信息/注入检测后冻结 | （尚未接入执行器，暂无端到端指标） | 已生成并通过校验，但还没有被驱动真实 Agent 运行——明确标注为未完成，不算作已支持 |

## 5. 设计取舍

**为什么确定性规则和 LLM Judge 要分开，而不是都交给 Judge？** 安全类硬规则（引用是否越界、有没有编造法条）必须是确定性的、可以扩展到大样本的，如果交给 LLM Judge 打分，会引入本不必要的不确定性，而且成本高得多。只有真正无法用规则表达的语义维度才值得花钱调用 Judge。

**为什么资格筛选和效果测量要严格分离？** 如果筛选规则本身依赖被比较双方的表现，相当于"先看了答案再决定考不考这道题"，消融实验的结论会失去说服力——这是本项目消融设计里最容易被忽略、但也是最关键的一条纪律。

**为什么坚持报告未达标的结果？** Reviewer 检出率 87.5% 低于 90% 门禁，报告选择直接写"不能宣称质量门禁通过"而不是换个说法回避。这个取舍背后的逻辑是：一份会隐藏坏消息的评测报告，慢慢会失去被信任的资格，不如老实报告问题、把它列为下一步优化方向。

**为什么小样本实验（n=3、n=6）还要保留在文档里？** 它们不能用来外推生产表现，但可以用来验证"消融设计本身是否 work"、发现工程 Bug、演示方法论——报告把这类结果和大样本结果物理分区，而不是删掉或混在一起，是为了让读者知道每个数字的可信边界。

**为什么要提供"从图中间冻结开始跑"这种单 Agent 消融方式，而不是永远跑完整三 Agent 图？** 如果永远从头跑到尾，Reviewer 检出率的波动里会混进上游判断是否正确、检索是否命中这些环节的噪声，出了问题很难判断锅在哪一层。冻结上游产物、让被测的那个 Agent 在真实生产代码路径上跑，是"单 Agent 消融"和"单元测试"这两种思路在 Agent 系统里的结合。

**为什么评测分级里"记账"和"拦截超支"是两件独立的事，目前只接了前者？** 拦截接口在生产线上路径上是必需的——线上流量不能因为一次意外预算超支就把服务打挂。但评测脚本目前的做法是先离线估算一次成本，再手动决定要不要跑，跑完才如实记账——这更接近"人工审批 + 事后台账"，而不是自动化门禁，是一个明确可以改进但目前还没接上的地方（详见 §7）。

## 6. 易错点

- **把门禁目标值当成实际成绩**："要求 Recall@5 不回退"是门禁条件，不是"Recall@5 提升了多少"这个实际结果——混用这两者会让报告显得比实际情况更好。
- **样本量相同就假设两组实验可比**：n=100 的两组实验可能测的是完全不同的变量（比如一组测检索模式、另一组测精排选择），不能只凭样本量一样就直接横向比较数字。
- **只报告收益、不报告代价**：BGE 精排提升排序的同时带来约 1.3 秒的延迟增加，报告如果只说"提升了排序质量"而不提延迟代价，读者会做出错误的成本估算。
- **字符串匹配指标和语义 Judge 结论冲突时，直接采信更好看的那个**：本项目事实忠实度实验里就出现过字符串检查把"旧记录已被正确更正"误判为"泄漏旧事实"的假阳性，正确做法是记录这个冲突并标注"需要升级为 Claim/Negation-aware evaluator"，而不是挑一个更好看的数字写进结论。
- **测试样本或提示词泄漏进了评测/提示词本身**：如果评测样本的措辞出现在系统提示词或 few-shot 示例里，模型等于"提前看过题"，分数会虚高但不代表真实能力，这是评测设计时要主动检查的数据泄漏风险。
- **把"分级执行"当成代码强制的门禁**：像本项目 `compare`/`release` 这类分级，如果背后没有真正的差异化代码逻辑，本质是团队约定而不是系统性保障——读到"分几级评测"时，多问一句"这几级之间的边界是代码强制的，还是靠人记得"。
- **以为记了账就等于有预算拦截**：评测/线上预算系统如果只做"事后记录用量"，不做"超支前拒绝执行"，本质上防不住真正的超支——这是两个独立的能力，接了一个不代表接了另一个。

## 7. 生产化差距与面试应对

本项目的评测体系在方法论纪律上（分层、消融、盲选、诚实披露）已经相当完整，对照 §2.6 的"完善评测体系"清单逐项看，离生产级还有几处明确差距：

| 维度 | 本项目现状 | 生产环境通常怎么做 | 面试怎么答 |
|---|---|---|---|
| 数据标注来源 | 全部为合成数据或源数据派生集，未经真人标注 | 人工标注平台产出的真人标注基准，通常配合标注者间一致性指标 | "当前样本明确标注为合成/派生数据，不冒充人工标注；生产化第一步是投入真实法律专业人士标注一批黄金集" |
| 评测触发方式 | 手动执行分级脚本，分级之间的边界更多是团队约定而不是代码强制的差异化逻辑 | 接入 CI/CD，代码或 Prompt 变更时自动触发回归评测，阻断有回归的合并 | "当前评测是手动分级执行；生产化会把确定性规则那一层接入 CI，用代码而不是约定去区分级别" |
| 评测资源预算的强制力 | 预算系统已经具备"超限就拒绝执行"的拦截能力，但评测脚本目前只用了"事后记账"的那一半 | CI/CD 里的评测网关在发起真实调用前就用配额系统拦截，超限直接失败 | "预算记账已经做了，但还没有接成'超支就跑不动'的强制门禁；这是从'人工看着预算跑'到'系统自动拦截'之间的差距" |
| 在线评测 | 无持续在线抽样评估，相关配置项甚至还没有被任何代码读取 | 对生产流量做抽样异步评测，配合隐式反馈持续监控质量漂移 | "线下消融证明了改动有效，但线上还没有持续监控；这是从'一次性验证'到'持续质量保障'之间实打实的差距" |
| 统计显著性 | 报告绝对/相对变化，未做显著性检验 | 大样本场景通常会做假设检验或置信区间估计，判断观察到的差异是否显著 | "当前样本量下，主要通过控制变量和盲选来保证结论可信，还没有引入正式的统计检验；样本量足够大之后应该补上" |
| Golden Set 漂移监控 | 无 | 定期在固定标准样本集上重跑，观察分数是否随模型/索引更新退化 | "当前每次实验是独立跑一次；生产化应该建一个固定的回归基准集，每次发布前自动重跑对比" |
| 人工审核回流 | 用户反馈落库但未形成标注回流闭环 | 低分/点踩样本进入人工审核队列，审核结果回流成新的评测/训练数据 | "反馈已经持久化，但还没有形成'低分样本 → 人工审核 → 回流评测集'的完整闭环，这是生产化的下一步" |
| 多轮/并发场景评测 | 数据生成和冻结管线已打通，但没有接入真正驱动 Agent 的执行器 | 场景数据接入真实的集成测试执行器，在 CI 或定期任务里驱动真实流程 | "数据生成和冻结管线已经打通并通过了自检，但执行器这一环还没接上；诚实说清楚差在哪一步，比含糊说'已支持多轮场景测试'更重要" |

## 8. 动手验证方式

1. 分别跑一次零成本 profile 和本地真实调用 profile，对比两次报告里字段的差异，理解为什么前者产出的数字不能代表 Agent 真实能力。
2. 找一组本项目已经跑过的消融实验（比如 BM25 vs Hybrid），检查两份报告的数据集哈希、索引指纹、`top_k` 是否完全一致——这是判断"这组对比是不是真正的单变量消融"的第一步。
3. 故意构造一个"字符串匹配指标和语义判断会冲突"的样本（比如回答里出现了"旧记录已被更正为新值"这类否定语境表述），观察确定性 Evaluator 和 LLM Judge 是否给出不一致的判断，体会为什么两种方法要并存而不是只选一种。
4. 找到盲选筛选阶段"关闭精排"这个配置项，思考：如果筛选时也打开精排，盲选还成立吗？为什么"筛选配置"本身也要作为盲选纪律的一部分被检查，而不只是看筛选规则的文字描述。
5. 对比资源预算类里"检查并拦截"和"只记账"两类接口的实现，再确认评测脚本实际调用的是哪一类——体会"预算记账"和"预算拦截"在代码里可以是完全独立的，接了前者不代表接了后者。

**自测题：**

- 如果一组消融实验的"资格筛选规则"会读取 Candidate（比如 BGE 精排后）的实际排序结果来决定样本要不要进入最终对比集，这个消融实验的结论还可信吗？为什么？
- Reviewer 检出率、误拒率、动作准确率这三个指标，分别对应经典分类问题里的哪些概念（提示：想想 Precision/Recall/混淆矩阵）？
- 单独测 Reviewer 时把上游产物冻结、只让 Reviewer 在真实代码路径上跑。如果这次评测发现 Reviewer 检出率很低，这个结果能不能说明"三 Agent 编排整体表现差"？为什么单 Agent 消融的结论边界比端到端消融更窄，同时又比纯 Mock 更可信？
- 如果面试官追问"你们怎么保证高成本级别的评测不会被误当成低成本级别的小样本跑掉"，诚实的回答应该承认什么、又该强调哪一部分是有代码保障的？
